## A. Download log (`pikpak_wms/store`, new table `downloads`)

1. **Columns:**
   - `id`, `file_id`, `name`, `size`, `hash` (PikPak gcid if known), `dest_path`;
   - `plan_id`, `status` (`done|failed|cancelled|skipped_exists|marked`), `reason`;
   - `started_at`, `finished_at`, `avg_mib_s`, `links`, `peak_connections`;
   - `source` (`plan|manual|backfill|scan`), `user_id`.
   Write a row on every outbound attempt. `marked` means the owner said the file was already downloaded (§C.2).
2. **Backfill once at migration** (idempotent):
   - every applied outbound action in `audit` (plans 59, 60, …);
   - a scan of the library roots used by the layout (default `资源/整理/**` under `LIBRARY_DIR`), matching files to the index by name and size, with `source=scan`.
3. **CLI:** `wms downloads [--today|--since ..] [--name X] [--status ..] [--json]`.
4. **Bot: `/downloads`** (menu `下载记录`), owner only.
   - Shows today's and recent rows: name, size, status, time, speed and destination.
   - Search with `/downloads juvr00309`.
   - Buttons: `今天`, `近7天`, `失败的`.

## B. Skip what is already there

1. **Before each outbound file:**
   - **The destination file exists with the same size:** skip it as `skipped_exists`. With `OUTBOUND_VERIFY=hash`, also compare the gcid; if it differs, download to `<name> (2).ext`. Never overwrite.
   - **The same name and size are known in `downloads`** (status `done|marked|scan`) at another path: skip it with the note `已在 <path>`. Turn this check off with `OUTBOUND_SKIP_KNOWN=false`.
2. **Plan rendering** lists these files up front as `已下载过，将跳过（N 个，X GiB）`, so the confirm screen shows only the real work.
3. **A plan whose items are all already present** (like plans 63–66) says so and offers no `执行` button.

## C. NL: "not downloaded yet" and exclusions

1. **New filter `not_downloaded: true`.**
   - It excludes anything with a `downloads` row (status `done|marked|skipped_exists|scan`) for the same file_id, or for the same name and size.
   - Phrases that trigger it: "未下载", "还没下", "没下载过", "还未下载过", "新的（相对 NAS）" and similar. Add them to the rules layer **and** to the few-shot examples.
   - The plan explanation shows `· 只含 NAS 上还没有的文件（对照下载记录）`.
2. **Exclusion and "already downloaded" remarks:** "X 下过了", "X 已经下了 / 已下载", "不要 X", "除了 X", "X 不用", "跳过 X".
   - **Inside a request** ("…的视频下载，juvr00309 下过了"): the main intent stays. X becomes an exclusion (`exclude_names` / `name_not_regex`), and X also gets a `marked` download row so the remark is remembered.
   - **On its own as a follow-up:**
     - If the same user has a pending NL plan from the last 30 minutes, remove the matching items from **that** plan, re-render it, and reply 「已从计划 N 中去掉 X（M 个文件）」.
     - If there is no pending plan, record a `marked` row and reply 「记下了：X 已下载，之后不会再下」.
     - **Never** create a download plan from such a sentence.
   - **Safety guard:** a sentence that only names files and says 下过了 / 不要 must never produce an action plan. Add the guard and tests for it.
3. **Eval:** add Saki's real sentences from §Evidence to the eval set, with the expected outputs above.

## D. Parallel downloads and per-file cancel

1. **Files in parallel.**
   - A plan downloads up to `OUTBOUND_PARALLEL_FILES` files at once. The default `0` means no limit, as Saki asked. Several running plans may also download at the same time.
   - Saki can change the value in the bot: on the plan's confirm/progress message (`同时下载：1 / 2 / 4 / 不限`), and as a global default under `/settings` or `/proxy`. Say in HANDOFF which one you chose.
2. **Shared connection budget.**
   - All files share `OUTBOUND_MAX_TOTAL_CONNECTIONS` (default 32). The M9.1 per-file ramp works inside this pool.
   - "Unlimited files" therefore cannot open hundreds of connections and trigger the CDN's 503s.
   - Files beyond the budget wait for connections, not for each other.
3. **503 is not fatal.** On 429/503 from the CDN:
   - reduce connections (as in M9.1);
   - back off exponentially, from 5 s up to 2 min;
   - relink after 2 failed attempts;
   - keep going for up to `OUTBOUND_RETRY_MINUTES` (default 30) before marking the file failed.
   Plan 66's first file failed in exactly this way.
   **The same applies to connection errors** (`ClientConnectorError: Cannot connect to host dl-*.mypikpak.com:443`, resets and timeouts). Plan 66 finished with 5 files applied (average 1.98–3.82 MiB/s, web+origin, 16 connections) and 4 failed: one 503 and three `Cannot connect to host` errors on different dl-a10b hosts, each after hours of good transfer.
4. **Progress message.**
   - One line per active file: name, %, MiB/s, connections.
   - A summary line: done / failed / skipped / total, aggregate speed, ETA.
   - Paged when there are many files.
5. **Per-file cancel.**
   - Each active or queued file line has a `取消` button.
   - It stops that file only and keeps its `.part` and `.part.state`, so a later run resumes it. The file is recorded as `cancelled`; the others continue.
   - Add `重试失败的` once the plan finishes.
6. **Per-file state.** M8.3's stop/continue and restart recovery keep working for each file.

## F. M9.1b (carried over): confirm before probing

1. **Setting:** `PROXY_PROBE_CONFIRM`, default true.
2. **The ask.** A scheduled probe, and the first one after start, sends the admins:
   - text: 「要现在给节点测速吗？最多约 150 MB 代理流量（≈¥0.01）」
   - buttons: `立即测速` / `跳过本次`
   Only one ask may be pending at a time.
3. **The answers.**
   - `立即测速` runs the probe and edits the message to show the result table.
   - `跳过本次` skips until the next schedule.
4. **CLI:** `python -m tgmd.traffic ask-probe` writes a request row into `traffic.sqlite3`. The running bot checks for it at most every 30 s and sends the same ask. This lets Cowork trigger it without touching the Telegram session.
