### 真实事件流样本

来源：`wms events --raw --limit 20`。链接、缩略图和文件名已去掉。

- 顶层是 `{next_page_token, events:[…]}`，**新的在前**。已核对：20 条的 `created_time` 严格递减。
- 单条事件：
  ```
  kind: drive#event
  type: TYPE_RESTORE          # 转存；这 20 条全是 RESTORE
  type_name: Add
  id: <事件 id>
  created_time / updated_time: 2026-10-01T00:34:52.864+08:00
  file_id: <文件 id>           # 顶层就有，和 reference_resource.id 相同
  file_name: <名称>
  folder_id: <父目录 id>
  reference_resource:
    kind: drive#folder | drive#file
    id / parent_id / name / size / hash / mime_type
    phase: PHASE_TYPE_COMPLETE
    params: {db_modify_time, original_share_id, platform: Telegram, …}
    created_time / modified_time
  ```
- 结论：
  - 待决问题 1 的两个假设都成立：`file_id` 在顶层；新的在前。可以把「可能的 id 位置」收紧到 `file_id`，其他位置作为兜底保留；
  - 转存来的通常是**整个目录**（`reference_resource.kind = drive#folder`），和简报的设计一致。
- **还缺的验证**：用户转存新内容之后，确认事件同步能把它收进索引。等用户在 Telegram 里完成测试，由 Cowork 回报。

## A. 模型输出失控，导致主机被误判离线（必修）

**现象**：
1. 个别句子上，模型输出失控：temperature 0 加 json_object 格式时，模型会停不下来，一直输出。
2. 60 秒后 `TimeoutError`。按 M8.2 §E 的逻辑，重新探测成功后，这句话会再生成一遍，又是 60 秒超时。
3. 第二次超时后主机被判定离线。之后 60 秒内，**所有句子**都立刻返回「every model host is offline」。

每次出事的句子不一样，比如「把/Media里超过半年的文件归档」「把视频归档」。单独重跑其中一句，3 秒就能正常返回。

在 bot 里，这意味着：用户发一句模型处理不了的话，要干等 2 分钟；接下来 1 分钟里发的所有句子，都会被告知「模型主机离线」。

**修法**：
1. **给输出长度设上限**：请求体里加 `max_tokens`，默认 512，可以用 `NL_OPENAI_MAX_TOKENS` 调整。Ollama 的 OpenAI 兼容接口会把它映射成 `num_predict`。
   - 实测：设成 400 后，原来会超时的 3 句变成 `answer cut off`，每句 2～10 秒就结束了。
   - `answer cut off` 只算**这一句**失败，回复「这句我没理解好，换个说法试试」，不影响主机的在线状态。
2. **生成超时，但主机探测正常**：说明是这句话本身的问题，不是主机掉线。
   - 这一句直接失败，不重试（重试又要等一次超时），不把主机判离线；
   - 只有连接被拒绝、连接被重置、探测失败，才算主机离线。
3. **生成超时时间**：`NL_OPENAI_TIMEOUT` 的默认值从 60 秒降到 30 秒。有了 max_tokens，正常的句子在 10 秒内就能完成。
4. **评测里一句失败不能连累后面的句子**：
   - 每一句开始前都要重置主机状态，或者对每一句都独立探测一次；
   - `errors` 按原因分开计数：`cut_off`、`timeout`、`offline`。
5. **测试**：
   - 超时，探测成功 → 只有这一句失败，下一句照常翻译；
   - `max_tokens` 写进了请求体；
   - `answer cut off` 不改变主机状态。

## B. 时间方向：给出了两个边界时，方向也要能纠正（必修）

**现象**：「把 /Media 里超过半年的文件归档」，模型给的是 `created_after = 半年前`、`created_before = 现在`，也就是「最近半年」，方向正好反了。

M8.2 的 guard 只在「只给了一个边界」时才纠正，这种情况漏掉了。「三个月前」「30 天以前」也是一样的写法。

**修法**：原句被判断为「更早」方向，同时满足下面两条时，改成 `created_before = 原来的 created_after`，并删掉 `created_after`：

- 模型给出了 `created_after`；
- 模型给的 `created_before` 离现在不到 1 天，或者根本没给。

计划里同样标注「已按原句更正时间方向」。

**加测试**：「超过半年」「三个月前的视频」「30 天以前的文件」，这三句都要纠正成 `created_before`。

## C. 去掉原句里没有依据的条件（建议做）

模型常常凭空加条件：

- 句子里没提大小，却加了 `min_size`、`max_size`，比如「整理一下 /Cosplay」；有时两者还相等，比如 `min_size = max_size = 100 GiB`；
- 句子里没提时间，却加了时间条件，比如「清理名字包含广告的文件」；
- 句子里没提名字，却加了 `name_contains`、`name_regex`。

**修法**：只对**模型**的结果做词面依据检查（rules 的结果不做）。

- 原句里没有大小相关的词（GB、MB、KB、大于、小于、超过 N、大文件、小文件）→ 丢掉 `min_size`、`max_size`；
- 没有时间相关的词（天、周、月、年、今天、昨天、之前、以来、最近、日期数字）→ 丢掉 `created_after`、`created_before`；
- 没有「名字 / 名为 / 叫 / 包含 / 开头 / 结尾 / 带」这类词，也没有引号 → 丢掉 `name_contains`、`name_regex`；
- `min_size == max_size`，并且原句里没有「等于」→ 两个都丢掉。

每丢一个字段，都在 `corrections` 里记一笔。计划里显示「已去掉原句没有提到的条件：大小」。

## D. 规则层再补几条（建议做）

- **否定句**：「不要 / 别 / 不用」后面跟着动作（删除、移动、下载……），比如「不要删除 /Inbox 里的视频」→ 回复「好的，不做任何操作」，不交给模型。
- **「本周」「今天」的上界**：模型会写 `23:59:59` 或者下一天、下一周的开头。评测的等价比较里，把「当天 23:59:59」也算作自然边界。
  - 「本周」的起点：模型有时写成周四或周五，这属于**真错**。系统提示里补一句「一周从周一开始，本周 = 本周一 00:00 起」。
