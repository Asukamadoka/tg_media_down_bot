# M9.6: subscription revival (bot side)

> Drafted by Cowork, 2026-10-07. Baseline: 395e806 (after M9.5.1). Bot UI text is Chinese; code, docs and commits are English.
> Privacy: no provider name, domain, subscription URL, mailbox, address or account value in code, docs, tests, fixtures or commits. Use `https://sub.example.invalid/...` and invented node names. The real values live in Saki's private vault and in the proxy container's config only.

## Why

The proxy subscription (a prepaid, pay-per-GB provider) runs out of balance now and then. Its normal renewal path is a human one: log in with an e-mail magic link, read the balance, delete the account (the provider's own "renew" button), register again with the same mailbox, copy the new generic subscription link. Saki does that by hand. Everything around it is slow and easy to forget: noticing the subscription is dying, remembering the steps, validating the new link, switching mihomo without breaking Telegram for the bot, and rolling back when the new link is bad. This milestone automates those, and nothing else.

## Split of work (fixed)

| Bot automates | Saki does by hand, always |
|---|---|
| A. Detect a near-expiry or dead subscription | Log in (e-mail magic link) |
| B. Push a Telegram checklist with the login steps | Delete the account (the renew button), register again |
| C. Accept the new subscription URL from Saki | Copy the new subscription link |
| D. Validate it (fetch DIRECT, parse nodes, sanity checks) | |
| E. Switch mihomo to it, with backup and rollback | |

Hard limits (red lines for this milestone):

- The bot never opens a mailbox, never reads mail, never follows a login link, never creates or deletes a provider account, never types on the provider site.
- The bot never sends a command or message on Saki's behalf. It only answers messages Saki sends it.
- No mailbox-reading step (Spark, Gmail, IMAP) is built. A decision is pending with Saki. Keep one clean entry point (`SubscriptionService.accept_url`) so a future source could call it; build nothing for it.
- This is the provider's normal renewal path, not fee evasion. Do not add anything that hides the account or defeats the provider's checks.
- Restart `bot` only, never `proxy`. Back up every file before it is replaced.

## A. Detection

New `tgmd/subscription/detect.py`. Pure functions over a snapshot, so every rule is testable.

Signals, each with a stable name:

1. `fetch_dead`: the bot's own periodic fetch of the stored URL (DIRECT, every `SUB_CHECK_HOURS`, default 6) answers 401, 403 or 404. A 5xx or a network error is `fetch_unknown`, never dead.
2. `nodes_dead`: M9.1's rule (≥ `DEAD_RATIO` of real nodes dead for 10 minutes). Reuse its numbers, do not duplicate the state machine.
3. `sentinel`: a node whose name matches `SUB_SENTINEL_REGEX` is in the provider (the provider puts a "top up to unlock more nodes" pseudo-node into the list when the balance is low). Default regex empty = signal off. The real phrase is a private value.
4. `nodes_shrunk`: the number of real nodes dropped by ≥ 30 % against the last healthy snapshot.
5. `userinfo_expiry`: if the provider's `subscription-userinfo` header carries `expire` or `total`/`download`, warn when `expire` is within `SUB_WARN_DAYS` (default 3) or less than 5 % of `total` is left. UNVERIFIED: today the provider returns an empty value, so this signal is expected to stay silent. Write it, test it with a synthetic header, do not rely on it.

Pseudo-nodes (names matching the sentinel regex, or `DIRECT` / `REJECT`-like entries) are not "real nodes". Real-node counting already exists in `nodes.py`; share it.

State: `ok` → `warning` (sentinel or shrunk or userinfo; one soft notice) → `dead` (fetch_dead, or nodes_dead). Only `dead` and `warning` start a revival case. One open case at a time.

**Balance trend is not observable by the bot.** The balance exists only on the provider site, behind the login. Saki's rule of thumb (balance ≤ -9 means near expiry) stays a human check in the checklist. Optional, only if it costs under 40 lines: `/sub balance <number>` stores a manual reading with a timestamp; with two or more readings the status shows the daily slope and the projected day it crosses the threshold. If it grows, drop it.

## B. Checklist push

When a case opens, the bot sends Saki (admin chats only, same notify path as M9.1) one message:

- What it saw (signal names in plain Chinese, node counts).
- The numbered steps. The mailbox is **not** written in the message: the text says "the mailbox on file" and where Saki's private note is. Steps, in order: open the provider login page (the text says "the provider's login page", no URL in the repo; Saki's private config can supply an optional `SUB_LOGIN_HINT` env string that is shown verbatim and never logged); choose e-mail login; open the newest login mail; check the balance (≤ -9 means expiring); press the account-deletion button; repeat login; the balance should now be 0; open the "subscription" section; pick the generic subscription; copy the link.
- Buttons: 「我已拿到新链接」(arms the next message as the URL, 10 minutes), 「6 小时后再提醒」, 「这次不处理」.
- Reminder policy: at most 3 reminders, 12 hours apart, then silent until the signal clears and returns. Recovery message when the signal clears on its own.

i18n: add keys to the catalog in both languages. Command names and callback data are not translated (i18n red lines).

## C. Accepting the URL

- Entry points: `/sub <url>` and, after the 「我已拿到新链接」 button, a plain message that parses as one http(s) URL. Admins only (`ADMIN_USER_IDS` / the existing admin check). Anyone else: ignored silently.
- Only a URL that arrives in a message Saki sent. Nothing is fetched from a mailbox, a clipboard or a file.
- Right after reading it the bot tries to delete the message that held the URL (Telegram `delete_messages`); a failure is logged without the URL.
- URL hygiene: `http` or `https` only, length ≤ 2048, no userinfo in the host part, no `file:` / `ftp:`. The host must not resolve to a private or loopback address unless `SUB_ALLOW_PRIVATE=1` (SSRF guard; the URL comes from a chat).
- Redaction helper `redact_url()`: scheme + host + `/…` only. Every log line, alert, exception message and test failure message uses it. Never `repr` a URL.

## D. Validation (nothing changes in production yet)

`tgmd/subscription/validate.py`, pure parse plus one injected fetch.

1. Fetch DIRECT with a 15 s timeout, 2 MB cap, `Accept-Encoding: gzip`, the provider-expected User-Agent from `SUB_FETCH_UA` (default a mihomo-like string). The bot lives in the proxy's network namespace, so "DIRECT" means: mihomo's rules must route the subscription host DIRECT. Before the fetch, check that (`GET /connections` for a recent connection to that host, or the M9.1 direct list). If the host would go through a node, stop with a clear message ("add the host to the direct list first"), never fetch through a node.
2. Parse two formats: mihomo/Clash YAML (`proxies:` list) and the base64 URI list (`vless://`, `hysteria2://`, `trojan://`, `ss://`, `vmess://`). Use the same YAML loader the repo already depends on. Anything else: reject with "unknown format".
3. Sanity: ≥ `SUB_MIN_NODES` (default 3) real nodes; every node has a non-empty server and port in 1..65535 and a type from an allow-list; names unique after trimming; no node of type `direct`/`reject`; at most 500 nodes; the content is not byte-identical to the currently active one (say so: "same as the current subscription, nothing to switch").
4. Compare with the current provider: show old vs new counts and the protocol mix. Show node **names with prices** (existing `pricing.py` parsing) only in the admin chat, never in logs.
5. Output a `Validated` object (parsed nodes, normalized provider YAML text, counts, digest). No URL inside it.

## E. Switch with backup and rollback

The bot cannot edit mihomo's config (and must not: the whitelist forbids `PUT /configs`). So the node list moves into a **file provider** the bot owns, exactly like the M9.1 direct-rules file:

- One-time NAS change (Saki's yes needed, see "NAS needs"): provider `main` changes from `type: http` to `type: file`, `path` in the mounted writable directory, same `health-check`, same groups. The previous config is backed up first.
- Bot-side switch, in this order:
  1. Write the new provider YAML to `<file>.new`, `fsync`, then keep the active file as `<file>.bak-<UTC timestamp>` (keep the last 5, delete older), then atomic `rename` of `.new` over the active file.
  2. `PUT /providers/proxies/main` (add exactly this path to `_ALLOWED_WRITES`, nothing wider). UNVERIFIED: that mihomo 1.19 re-reads a file provider on this call. Gate: the NAS spike below must confirm it, otherwise the fallback is a `PUT /configs` reload that needs Saki's decision, and the bot stops with an instruction instead.
  3. Verify within `SUB_VERIFY_SECONDS` (default 120): provider `updatedAt` moved, real-node count equals the validated count, and at least `SUB_VERIFY_ALIVE` (default 1) node answers a delay test through the existing probe. Telegram reachability is checked last through the `TG` group's current exit (`current_exit`).
  4. On any failure: restore the newest `.bak`, `PUT` again, verify the old state, alert Saki "switched back" with the reason. If the old file is itself bad, say so plainly; do not loop.
- Success: the new URL replaces the stored one (DB, key under the existing kv helper; never logged), the case closes, one summary message (counts only), one log line without the URL, an audit row.
- Idempotent and re-entrant: a restart in the middle of a switch finds a `switching` case and finishes or rolls back; it never leaves `.new` behind.
- Periodic refresh: since the provider is now a file, the bot re-fetches the stored URL every `SUB_REFRESH_HOURS` (default 12) through the same validate-and-switch path with `silent=True` (no message unless it fails or the nodes changed by ≥ 30 %). This replaces mihomo's own `interval`. A failed refresh never writes the file.

## F. Case state machine

States: `open` → `awaiting_url` → `validating` → `staged` → `switching` → `done`, plus `failed` and `snoozed`. Persist in the DB (new table `sub_case`, only adds, per CC_BRIEF §1.3): id, state, signals JSON, opened_at, updated_at, reminders, last_error (no URL). The stored URL is a kv value, not in `sub_case`.

`/sub` (admin) prints: provider state, node counts, last refresh, open case state, backups available. `/sub switch` re-runs the last staged validation; `/sub rollback` restores the newest backup (confirm button first).
